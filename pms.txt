# Задача: добавить третью роль INVESTOR и разделить видимость денег по ролям

Сначала прочитай AGENTS.md и docs/PROJECT_INDEX.md. Не читай и не копируй .env, базу, загруженные документы и секреты. Исходники и миграции — источник истины, индекс — карта.

## Цель
Сейчас в проекте две роли: OPERATOR и ADMIN. Нужно три, с жёстким разделением по деньгам:

- OPERATOR — как сейчас, видит и делает всё. Поведение не должно измениться.
- ADMIN — работает с жителями, комнатами, заявками и задачами, но НЕ видит никаких денег: ни сумм, ни оборота, ни цен, ни балансов, ни долгов, ни платежей, ни расходов.
- INVESTOR — только чтение и только агрегированные финансовые итоги. Никаких имён, телефонов, документов, комнат и списков жителей.

## Матрица доступа (по умолчанию)

| Ресурс | OPERATOR | ADMIN | INVESTOR |
| --- | --- | --- | --- |
| Дашборд | полный | только заполняемость, без денег | только итоги денег |
| Жители (список/карточка) | полный | без цены, баланса, долга, периодов оплаты, истории платежей и сумм в журнале изменений | нет (403) |
| Комнаты | полный | без цены | нет (403) |
| Платежи и корректировки | полный | нет (403) | нет (403) |
| Расходы | полный | нет (403) | нет (403) |
| Отчёты | все | только нефинансовые (жители без денег, заполняемость) | только сводный финансовый отчёт по месяцам, без строк по жителям |
| Заявки (admissions) | полный | без сумм; тариф подставляется сервером или одобрение требует оператора | нет (403) |
| Задачи | как сейчас | как сейчас | нет (403) |
| Уведомления | свои | свои, без текстов с суммами (напоминания об оплате не приходят) | нет |
| Аудит, пользователи, настройки (запись) | оператор | как сейчас | нет |

Новый эндпоинт GET /api/investor/summary (доступ: INVESTOR и OPERATOR), параметры: диапазон дат, группировка по месяцу. Возвращает только числа: выручка (платежи минус корректировки), расходы (без void), чистая прибыль, общая задолженность одной суммой, ряд по месяцам, опционально процент заполняемости одним числом. Без id, имён, названий комнат и свободного текста расходов.

## Критично: утечки сумм
Скрытие в React НЕ считается защитой. Всё делается на сервере:

1. Отдельные выходные схемы и сборщики ответов по ролям (в services.py и schemas.py), а не фильтрация на фронте. Денежные поля у ADMIN отсутствуют в JSON, а не равны null или 0.
2. Закрой побочные каналы для ADMIN: фильтры и сортировка по сумме, балансу, долгу и цене (отклонять параметры, а не игнорировать молча); поиск; CSV/XLSX/PDF-экспорты; тексты ошибок валидации и 409/422, где фигурируют суммы (например «переплата»); тексты уведомлений; журнал изменений жителя и BillingChange; admissions summary (начисления и оплаты); любые поля вроде price, tariff, amount, balance, debt, paid, revenue, total.
3. Прямые запросы по URL и по id должны давать 403, а не пустой ответ. Проверь IDOR.
4. INVESTOR не должен получать ни одного персонального или идентифицирующего поля, ни в каком эндпоинте.
5. Новые зависимости в dependencies.py (например require_money_access, require_operations_staff, require_investor_view). Никаких проверок роли через строки, разбросанные по handler-ам. Существующие get_current_user, require_operator, require_billing_permission не ломай.

## Данные и миграция
- Добавь INVESTOR в роли и в CHECK-ограничение users (новая Alembic-ревизия с upgrade и downgrade; применённые миграции не переписывай). Проверь на PostgreSQL и SQLite.
- POST /users и PATCH /users/{id}: оператор может создавать ADMIN и INVESTOR. Роль OPERATOR по-прежнему нельзя выдать через API. Администратор не может менять роли.
- Все новые чувствительные действия пишутся в аудит (автор, безопасные метаданные, без сумм и ПД в details для не-операторов).

## Тесты (обязательны)
- Параметризованный тест «роль × эндпоинт» по всем маршрутам из индекса: ожидаемые 200/403 по матрице.
- Рекурсивная проверка JSON: в ответах ADMIN нет ни одного денежного ключа из списка выше, ни в списках, ни в карточках, ни в журнале изменений, ни в ошибках, ни в уведомлениях, ни в экспортах.
- Инвестор получает 403 везде, кроме /investor/summary, /auth/me и разрешённого отчёта; в его ответах нет id, имён и комнат.
- Регрессия: поведение OPERATOR не изменилось.
- Миграция: upgrade и downgrade с новой ролью.
- Сумма в /investor/summary совпадает с данными дашборда оператора на одном и том же наборе записей.

## Спорные места — не придумывай, а действуй так и перечисли в финальном ответе
1. Может ли ADMIN регистрировать платёж? По умолчанию нет: платежи и расходы ведёт только оператор. Сделай так, чтобы это легко переключалось одной настройкой или зависимостью.

3. Показывать ли инвестору заполняемость одним числом? По умолчанию да, как агрегат.
